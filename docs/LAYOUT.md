# 中文换行：根因、修正与验证

## preview.7：词表未收录词

preview.6在词频表缺少词条时可能把一个词当成连续单字，因此既不触发词内断行惩罚，也未必属于短尾。例如“黯蓝”是有效词语，但固定词表输出“黯／蓝”；补标点、调短尾字数或改译文都不能补足这种识别缺口。

preview.7保留词典已识别的多字词，只重新考虑连续单字段。固定BMES成词位置概率形成最多8字的候选词，每个词独立计算起点与内部成本，再从右向左规划。这样在完整词边界开始的剩余文本，采用相同的后缀路径；无需共享可写缓存，不随逐行丢弃左文改变已选的后续词。仍由实际测宽决定可否移动，不改原文字节或引入存档内硬换行。

候选需要至少一个相对低频字：通用词频成本不低于2129，即上游保留词频总量约1/4096的阈值。它限制“中／出／了”“也／没／说”等常见单字误粘连，不是剧情专用例外表。该条件也可能漏掉合理的新词；概率模型本身仍有漏识别。它不重新判断词典已有多字词的歧义，不保证“雾蓝、浅绯”等所有未收录词都得到保护。词语超过行宽、特殊控制或安全条件不足时仍保留原生退化。

数据来自同一固定MIT上游的三份概率表，转成191,592字节只读GBK数据，生成过程只解析字面量，游戏内没有Python分词器、网络调用或大模型依赖。这里使用自有有界词候选图，不称为原版jieba整段HMM/Viterbi解码。来源、许可与再生方法见[第三方说明](../THIRD_PARTY.md)。

本地207项源码检查中203项通过、4项按平台条件跳过。实际生成的x86代码在两个映射基址执行319个中性用例，共638次调用，含16个精确断点断言；五个实际生成payload在三类ABI与两个基址完成92项桥接检查。新增样本涵盖多个未收录词、常见单字误合并与完整词后缀稳定性，不是独立标注的分词准确率评测。

三条玩家反馈的私有原译文另用原生取行代码连续提取至结束：六组字号参数、五种受控行宽，共90例/版本，已指定目标词拆分由4处降为0，闭标点坏切均为0，所有输出拼回原字节。字宽为受控缓存，不能称为GDI字体、游戏动画、全部字号真实画面或全篇验证。新版玩家包尚待构建发布，未操作正在游玩的游戏。

```text
python tools/build_native_oov.py --check
```

可用`--source-dir`指定三份固定概率表离线重现；默认从固定提交获取并验证SHA-256。玩家安装时不调用此生成器。

## preview.6：词典与标点规则

preview.6源码覆盖五个已识别PC v1.1中文引擎的三种二进制布局。日文、英文原版仍走各自既有字体路径；本页不宣称给日文接入中文分词。preview.6四个玩家包已发布，安装器在Windows与Linux CI完成两种视图启动检查；新版尚待实际游戏场景抽样，旧版Deck实测单独保留。

## 为什么有禁则仍会剩下闭标点

在原生TYPE0中，第一个闭标点可以放入当前行、后一个才超宽时，回退可能只带回第一个标点。使用正确GBK禁则表仍可得到下一行只有问号和闭引号的结果。对照让前一个标点先超宽，则会带回正文汉字，说明结果取决于超宽发生的位置；给配置补同一个标点不能消除这个分支缺口。

这是通过直接执行已识别1＋2原生取行、分类和复制代码复现的，字体后端与字宽受控，没有运行游戏入口。普通模式、正常状态及未改变缩进时也能发生，因此不把姓名格式、挂缩进或原译文手动换行当作已经证明的原因。

preview.5的补救层仅接受“一个汉字＋收尾标点”，会跳过纯标点以及两个汉字的尾行；它也没有词语边界。新的选择器在原生取行之后统一检查候选边界两侧，保留完整开闭标点约束，不为某个句子添加特例。

## 词语与尾行

通用词频数据固定于jieba上游提交，保留可编码GBK的1～8字汉字词（包括单字词频）。运行中的C代码用定点成本求词典DAG路径，再按以下优先级选择不晚于原生断点的候选：

1. 减少行首闭标点与行尾开标点。
2. 优先不拆下一行能够容纳的中文词、ASCII单词及数字串。
3. 对最终短尾作软调整，尽量保持足够正文；不按固定字数切句。
4. 在相同条件下尽量少移动。

词语过宽时保留按单元推进；原本两行能放下的块，不为尾行美观额外制造第三行。数据是通用词频，不包含游戏台词或玩家资料，也不等于所有歧义、专名都能分对。原译文、全半角标点、空格、显式控制与自然停顿不重写，不把物理换行存入历史或存档。

每次仅处理容量已核对的普通GBK／ASCII跨度，最多1023字节、512个单元；其他模式及不支持的控制状态保留原路径。未知字节、失败测宽、无可用宽度等不提交变更。先完整验证再写回，输出与pending拼接必须恢复原字节。

## 为什么还要统一测宽

三类引擎中，特定scale4模式的未缓存ASCII重绘／测宽路径额外减1，而取行路径没有。已对照mode、快进查询及四种缓存／后端状态；只取消该分支的单字节减1后，两条路径一致。非零缓存和CJK路径不执行该指令。修正只用于已识别中文引擎，不给所有ASCII统一补宽。

原生测宽还使用矩形中的两个临时字段。新探测复制完整108字节矩形，并使用下一行的实际起点，保留原矩形及当前光标；原生正常绘制继续使用自己的状态。

## 已执行的验证

- 源码200项检查，本地196项通过、4项按平台条件跳过；Windows CI为197项通过、3项跳过，Linux CI为192项通过、8项跳过。通用词表的独立结构、成本、筛选、归属与再生检查包含其中。
- 最终C字节在Windows x64的两个映射基址执行312个中性用例，共624次调用；包括9个精确断点和4个闭标点断言。检查栈、非易失寄存器、双1024字节缓冲区边界、原文无损、过宽退化和测宽失败。测宽回调故意改写副本字段，原108字节矩形保持。
- 三类原生度量路径合计384组模式／缓存对照，使用原生代码及受控字体后端，验证ASCII减1缺口和修正；不是实际GDI字体或游戏画面。
- 对玩家报告的两条原始译文，完整原生取行、分类、新桥接及通用词表在20种受控字宽／行宽组合中对照，共40例／版本。旧版有2处纯闭标点坏切、5处目标词拆开；新候选均为0，两版全部字节保全。原文仅保留在私有输入中；这不是全篇或实际字体的验证。
- 五个实际生成payload在两个重定位基址完成92项外层桥接检查，包括原生返回状态、flags、栈、调用次数、名字／控制守卫及探测副本。
- 五部中文实际构建的315份有效正文脚本、110份松散正文脚本与110份原译表保持；十组日英构建不调用中文原生层。最终增量只重建原生EXE，复用未改变的故事构建器检查。

这些层级不能替代游戏画面、历史返回、保存／读取、自动播放或所有字号的实际检查；旧版本实测仍按原版本单独保留。本轮未覆盖玩家正在运行的正式游戏，也未启动测试游戏；安装器的CI开窗检查不代表游戏运行或安装事务验收，不作全篇无故障保证。

## 维护者复现

默认单元测试无需编译器。使用已有Zig 0.16.0重现自有x86代码：

```text
python tools/regenerate_native_layout.py --compiler /path/to/zig --build-dir work/layout-rebuild-01 --check
```

在Windows x64及64位Python上执行无游戏、无GDI、无界面的真实x86检查：

```text
python tools/check_native_layout_runtime.py --compiler /path/to/zig.exe --output work/layout-runtime-01
```

输出必须是新目录，保留用例、编译日志和报告；工具不删除旧证据。其回调是受控测宽，不宣称原游戏已运行。词表再生用 `python tools/build_native_lexicon.py --check`，按固定上游与SHA获取数据；可指定本地原表及许可离线复现。声明与权利边界见 [THIRD_PARTY.md](../THIRD_PARTY.md)。
